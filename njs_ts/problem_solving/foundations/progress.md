# Track: foundations — JS as a problem-solving tool

Why this track: DSA theory is rusty and JS is new — patterns are useless while the language fights back. Each topic = the JS mechanics plus the costs that matter in problems.

| # | Topic | Why it matters | Status |
|---|---|---|---|
| 1 | The solving pipeline & test harness | The workflow *is* the skill; `node:test` = zero-install practice rig | 🟡 taught, exercise pending |
| 2 | Practical big-O: read constraints → pick target complexity | The ~10⁸ ops/sec rule turns input limits into the required algorithm class | ⬜ |
| 3 | Arrays: costs & idioms | push/pop O(1) vs shift O(n); slice copies; reference vs copy bugs | ⬜ |
| 4 | Strings: immutability, charCode math, build-don't-concat | String problems are a quarter of easy/medium banks | ⬜ |
| 5 | Map & Set (vs plain objects) | Frequency-counter and seen-set patterns power half of all "easy" tricks; Two Sum done right | ⬜ |
| 6 | Sorting: comparators & the lexicographic trap | `[10,9,1].sort()` → `[1,10,9]`; sort-then-scan opens many problems | ⬜ |
| 7 | Numbers: no ints, `%` of negatives, 2⁵³, floor division | Silent wrong-answer generators for people from typed languages | ⬜ |
