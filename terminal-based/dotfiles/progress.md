Tooling: **chezmoi** · **multipass + cloud-init** (Ubuntu VM) · **docker + devcontainers** (inside the VM) · Brewfile/`brew bundle` (Mac minimal) · age (secrets)
Legend: `[ ]` not started · `[~]` taught, awaiting demonstration · `[x]` demonstrated

## The artifact
A **three-layer reproducible dev environment**, every layer rebuildable from scratch in one command, resilient to unreliable internet/power (Egypt reality):

1. **macOS host** — minimal profile: only what must live on the Mac (Ghostty, AeroSpace, GUI apps via Brewfile).
2. **multipass Ubuntu VM** — the primary dev environment; provisioned by cloud-init (the same mechanism real cloud servers use).
3. **devcontainers** — per-project declarative envs running on the VM's docker engine.

## Founding design decisions
- **(2026-07-28) One repo for every machine** — differences live in template data, not repo boundaries. Machine dimensions per host: `os` (darwin/linux) × `role` (host/vm/server) × `ownership`. Alternatives considered: Stow, yadm, bare git repo, Nix home-manager (parked → `revisit/`; passion trigger acknowledged 2026-08-11, still held).
- **(2026-08-11) Linux-first inversion** — the VM is the primary environment; the Mac profile is the minimal complement. Ubuntu chosen for server-parity; multipass for cloud-init parity.
- **(2026-08-11) Project code lives INSIDE the VM's filesystem.** multipass mounts are SSHFS — too slow for `vendor/`, `node_modules/`, and file-watchers. The Mac reaches code via editor remoting (DF11), never the reverse; `multipass transfer` is for small exchange only (configs, dumps, the age key). Corollary: unpushed code dies with the VM — a feature; the rebuild ritual enforces commit hygiene.
- **arm64 everywhere** (M-series host): base images must be multi-arch/arm64; amd64 emulation in the VM is slow and out of scope.

- [ ] DF3. **Templates** — `.chezmoi.toml.tmpl` prompts on init; `{{ .chezmoi.os }}`/hostname/role conditionals; one config set rendering **Linux-default, Mac-conditional**. (Unlocks DF13 theme-as-data as a pull option — the fun hook.)
- [ ] DF4. **Migrate the nvim tree** — `exact_` directories (delete-what's-not-in-source semantics), lazy-lock.json policy (pin vs ignore), config-vs-state separation (`~/.config` vs `~/.local/share|state`).
- [ ] DF5. **multipass lifecycle** — launch/shell/exec/stop/delete/purge; explicit sizing (`--cpus 4 --memory 8G --disk 40G` — the defaults are useless for dev); snapshots (**stopped instances only**) vs delete/relaunch; where instance data lives (`/var/root/Library/Application Support/multipassd/` — root-owned, invisible to user `du`; ties to A9). Gotchas: backend = QEMU + Hypervisor.framework; NAT/DHCP IPs change across reboots (script `multipass info` → `~/.ssh/config`, never hardcode); VPN/macOS firewall can break VM DHCP (allow `bootpd` if launch hangs); clock drifts after Mac sleep (sporadic TLS/apt failures until timesync catches up); skip bridged networking — NAT + SSH is the pattern. **Pre-lesson: run the first `launch` the night before** (image download on Egyptian bandwidth).
- [ ] DF6. **cloud-init anatomy** — `users`/`ssh_authorized_keys`/`packages`/`runcmd`; plant the SSH public key here (DF11's editor attach rides on it); debugging via `/var/log/cloud-init-output.log`. Mental model: **runs once per instance** — editing the YAML never converges an existing VM; only the rebuild applies changes.
- [ ] DF7. **Packages as data** — Brewfile + `brew bundle` (Mac, minimal); apt via `run_onchange_` scripts reading one shared package list; tool lists as data files in the repo.
- [ ] DF8. **One-command bootstrap** — fresh VM → full shell env: `chezmoi init --apply` wired into cloud-init, **scoped secret-free** (encrypted targets template-guarded on key presence). Run as the `ubuntu` user, not root (`su - ubuntu -c '…'` — bare `runcmd` provisions `/root`). First-boot traps: unattended-upgrades holds the dpkg lock (prefer cloud-init's own `package_update`/`packages`, or set `DPkg::Lock::Timeout`) + `DEBIAN_FRONTEND=noninteractive`. Idempotency as the design rule; `run_once_` vs `run_onchange_` semantics. `--one-shot` noted for shared/ephemeral boxes.
- [ ] DF9. **Secrets** — what never enters the repo (keys, tokens, work identifiers); age encryption for the private few; **amend the DF8 bootstrap**: deliver the age identity out-of-band (`multipass transfer`), re-`apply` to materialize encrypted targets; why the key never rides in cloud-init user-data (user-data is readable from inside the instance and often logged).
- [ ] DF10. **Containers mental model** — install docker engine in the VM *as provisioning data* (extends DF7/DF8); images vs containers vs volumes vs bind mounts; build/run/exec/logs lifecycle; map the vocabulary onto the rdb-lab compose file already in daily use. Note: the Mac keeps Colima for that lab; the VM's engine is a second, deliberate runtime.
- [ ] DF11. **Devcontainers** — devcontainer.json spec + features + the `devcontainer` CLI (`devcontainer up` proves the spec editor-free). Editor attach, taught pattern: code lives in the VM → **nvim inside the VM** (the program's editor bet), or **VS Code Remote-SSH → "Reopen in Container"**; `docker context` over SSH = Mac-side CLI convenience only; JetBrains Gateway = the PhpStorm path — verify current state, expect friction. Exercise: a real PHP/TS project env, arm64 base images.
- [ ] DF12. **Offline survival kit** — know what each layer needs from the network and pre-empt it: apt archive cache + `--download-only` pre-fetch; **pre-build the devcontainer image + `docker save`/`load`** (features fetch from ghcr.io at build time — the hidden offline break); pin images by digest (arm64 manifest); multipass snapshot-restore as the reliable offline path (a fresh `launch` may still want the network). Exercise: assemble the kit + a written "what breaks offline" checklist. The actual network-off rebuild proof is DF14's final rep, not this lesson.
- [ ] DF13. **Theme as data — the Omarchy trick** (pull-eligible after DF3) — one semantic colorset in chezmoi template data; **capped at three targets: Ghostty + tmux + fzf** (`FZF_DEFAULT_OPTS`); LazyVim = named-colorscheme-per-theme (no highlight-group generation); bat/eza/btop as optional later reps. Note: Omarchy itself switches symlinked per-app theme files — the template version is deliberately more ambitious; verify Omarchy's current (2026) semantic system when drafting the lesson.
- [ ] DF14. **Capstone — the rebuild ritual** — destroy the VM → one command → working containerized dev env; **final rep runs network-off** (proves DF12); then round-trip one dotfile edit Mac → VM via `chezmoi update`. From DF5 onward, every lesson ends with a destroy-and-rebuild rep — reproducibility as habit, not finale.
